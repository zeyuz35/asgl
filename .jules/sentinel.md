## 2024-05-01 - [CVXPY canonicalization backend injection]
**Vulnerability:** The `canon_backend` parameter in `Regressor` was directly passed to the underlying `cvxpy.Problem.solve` without validation. While CVXPY implements some internal checks, a bare `try-except` block mapping standard Python `Exception`s or `ValueError`s can swallow unexpected errors from deeper levels (like missing backends or unsafe imports dynamically loaded by a backend), obscuring the root cause and potentially allowing unintended execution paths or denial of service if bad input is repeatedly provided.
**Learning:** Even though hyperparameter validation in local ML wrappers does not typically constitute a severe remote injection vulnerability, it is a crucial defense-in-depth practice. Unvalidated string inputs passed to complex dependencies (like solver backends) can trigger internal exceptions that are poorly handled, creating operational vulnerabilities or unexpected test/runtime failures.
**Prevention:** Implement explicit allowlists (e.g., `ALLOWED_CANON_BACKENDS = {"CPP", "SCIPY", "COO"}`) and validate string parameters strictly at the wrapper boundary (`_check_attributes`) before they interact with internal dependencies.

## 2024-05-01 - [CVXPY Solver Fallback and Exception Handling]
**Vulnerability:** The `solver` parameter in `Regressor` lacked input validation at the constructor/initialization level, and the fallback logic in `_solve_cp_problem` only caught specific CVXPY exceptions `(ValueError, cp.error.SolverError, cp.error.DCPError)`. This meant that passing an invalid object or encountering backend-specific exceptions (e.g., `mosek.Error` for missing licenses) bypassed the fallback mechanism entirely, bubbling up unhandled exceptions and breaking expected solver robustness.
**Learning:** Overly specific exception handling in adapter/wrapper classes for external dependencies (like solver backends) can inadvertently break intended fault tolerance if those dependencies throw proprietary or system-level exceptions. Additionally, strict type and domain validation at the wrapper boundary prevents invalid objects from entering deeply nested logic.
**Prevention:** Implement explicit type and domain validation for dynamic solver parameters using `cp.installed_solvers()` in `_check_attributes`. Broaden exception catching in fallback logic to a standard `Exception` or explicitly account for all known backend-specific exceptions to ensure reliable execution paths.
