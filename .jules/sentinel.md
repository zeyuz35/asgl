## 2024-05-01 - [CVXPY canonicalization backend injection]
**Vulnerability:** The `canon_backend` parameter in `Regressor` was directly passed to the underlying `cvxpy.Problem.solve` without validation. While CVXPY implements some internal checks, a bare `try-except` block mapping standard Python `Exception`s or `ValueError`s can swallow unexpected errors from deeper levels (like missing backends or unsafe imports dynamically loaded by a backend), obscuring the root cause and potentially allowing unintended execution paths or denial of service if bad input is repeatedly provided.
**Learning:** Even though hyperparameter validation in local ML wrappers does not typically constitute a severe remote injection vulnerability, it is a crucial defense-in-depth practice. Unvalidated string inputs passed to complex dependencies (like solver backends) can trigger internal exceptions that are poorly handled, creating operational vulnerabilities or unexpected test/runtime failures.
**Prevention:** Implement explicit allowlists (e.g., `ALLOWED_CANON_BACKENDS = {"CPP", "SCIPY", "COO"}`) and validate string parameters strictly at the wrapper boundary (`_check_attributes`) before they interact with internal dependencies.

## 2024-05-02 - [Boolean validation bypass via bitwise OR]
**Vulnerability:** In the `Regressor` logistic regression target validation, a bitwise OR (`|`) was used instead of a logical `and` (`(not is_binary_int) | (not is_binary_float)`). Because an input array cannot be simultaneously strictly integers and strictly floats, this condition evaluated `False | False` for valid inputs and `True | True` for invalid inputs, but it effectively meant the condition was `(not is_binary_int) and (not is_binary_float)`. Wait, actually using bitwise `|` on booleans in Python behaves mostly like `or`. The bypass was because valid arrays would make one boolean True, while invalid ones make both False. Using `|` was incorrect logic that allowed `y` targets to bypass the `{0, 1}` and `{0.0, 1.0}` strict target validation constraint.
**Learning:** Bitwise operators (`|`, `&`) should not be used as substitutes for logical operators (`or`, `and`) in explicit Python conditional checks, especially when validating security-sensitive data formats or arrays. Doing so often leads to subtle logic bypasses due to operator precedence or the semantic differences in how bitwise evaluation works compared to short-circuit logical evaluation.
**Prevention:** Strictly enforce the use of `and` and `or` for boolean logic in conditional statements. Reserve bitwise operators for element-wise operations on arrays. Write negative validation tests to ensure edge case inputs are correctly rejected by target validations.
