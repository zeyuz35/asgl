## 2024-05-01 - [CVXPY canonicalization backend injection]
**Vulnerability:** The `canon_backend` parameter in `Regressor` was directly passed to the underlying `cvxpy.Problem.solve` without validation. While CVXPY implements some internal checks, a bare `try-except` block mapping standard Python `Exception`s or `ValueError`s can swallow unexpected errors from deeper levels (like missing backends or unsafe imports dynamically loaded by a backend), obscuring the root cause and potentially allowing unintended execution paths or denial of service if bad input is repeatedly provided.
**Learning:** Even though hyperparameter validation in local ML wrappers does not typically constitute a severe remote injection vulnerability, it is a crucial defense-in-depth practice. Unvalidated string inputs passed to complex dependencies (like solver backends) can trigger internal exceptions that are poorly handled, creating operational vulnerabilities or unexpected test/runtime failures.
**Prevention:** Implement explicit allowlists (e.g., `ALLOWED_CANON_BACKENDS = {"CPP", "SCIPY", "COO"}`) and validate string parameters strictly at the wrapper boundary (`_check_attributes`) before they interact with internal dependencies.

## 2024-05-18 - [Target Type Validation Bypass]
**Vulnerability:** The `fit` method of `Regressor` used `sklearn.utils.multiclass.type_of_target(y) != "binary"` to short-circuit validation of binary targets for logistic models. `type_of_target` incorrectly considers any two-value set (e.g., `[-1, 1]`) as "binary", allowing targets other than `{0, 1}` to bypass the internal numeric validation. This could cause unexpected solver failures or incorrect optimization logic in `asgl`'s strictly `{0, 1}` formulation.
**Learning:** External library helpers (like scikit-learn's `type_of_target`) often have broader definitions than strict local requirements. Relying solely on them for security or strict state validation allows unintended data to bypass subsequent safety checks.
**Prevention:** Explicitly validate inputs against strict local requirements using logical checks (e.g., logical `and` with `np.isin`) rather than short-circuiting based on external generalizations.

## 2024-05-18 - [CVXPY solver backend injection and log forging]
**Vulnerability:** The `solver` parameter in `Regressor` was directly passed without validation, and its values were logged in `RuntimeWarning` messages upon failure. This could allow log forging or execution path injection via CVXPY's solver dispatch mechanism.
**Learning:** We must validate ALL string parameters, including solvers, strictly at the wrapper boundary before they interact with internal dependencies or loggers. Even though CVXPY ultimately errors out, exposing the raw strings in warning messages allows log forging, and not validating early hides the real issue.
**Prevention:** Validate user-supplied solvers against the explicit allowlist `cp.installed_solvers() + ["default"]` early in `_check_attributes` to fail fast and securely before execution or logging.
